    АРХИТЕКТУРА ПРИЛОЖЕНИЯ

    Как работает
    твой агент.

    Цель → решение модели → инструмент → результат → следующий шаг.

    01 / ПОСТАНОВКА

    Задача и ограничения

    Сохранить тренировку со снимка или объяснить историю. Модель не придумывает пропущенные показатели и не делает медицинских выводов.

    02 / МОДЕЛЬ

    Codex как исполнитель

    Локальный сервер запускает codex exec. Текст и снимок обрабатывает облачная модель; приложение получает структурированный JSON.

    03 / ИНСТРУМЕНТЫ

    Действие выбирает модель

    list_workouts читает историю, get_progress считает динамику, propose_workout готовит черновик. Их выполняет сервер.

    04 / ПАМЯТЬ

    История живёт в SQLite

    Модель получает нужные записи через инструмент. Контекст запроса временный, а сохранённые тренировки остаются после перезапуска.

    05 / ПРОВЕРКА

    Модель предлагает, ты проверяешь

    Сервер проверяет дату, диапазоны и дубли. Пользователь исправляет распознавание и подтверждает сохранение. У агента максимум четыре шага.

    06 / ГРАНИЦА

    Где агент, а где автоматизация?

    Загрузка файла, запись в БД и график выполняются по правилам. Агент выбирает, читать ли историю, считать ли динамику, уточнить запрос или подготовить запись.

    НАДЁЖНОСТЬ

    Проверки и ограничения

    Сервер проверяет даты, диапазоны значений и дубли. Модель получает ограниченный набор действий; повторный вызов уже выполненного инструмента останавливает цикл. Распознанные показатели сохраняются только после проверки пользователем.

    Инструменты реализованы функциями приложения. MCP, синхронизация с часами и работа нескольких пользователей в этой версии не реализованы.
